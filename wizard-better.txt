# wizard-better.txt

A running log of every friction point found while setting OpenSeek up for real.

Purpose: each entry becomes either a wizard step, a preflight check, or one
clearer line in the documentation. The goal is that the next person does not
have to discover these.

How to add an entry: append at the bottom with the date and a short title.
Keep the five fields. Mark the status as open, fixed, or wontfix.

## 1. 2026-11-07 - Telegram has no "StringSession" screen

**What I tried:** looked for a session string in the Telegram app, the web
client, and my.telegram.org.

**What happened:** it does not exist there. A StringSession is a Telethon
concept: a base64 blob containing the auth key and data-center id. It can only
be produced by running a Telethon login.

**Why it hurts:** the README says "log in with a Telegram user session" as if
that were one step. A first-time user has no idea a Python program is involved,
and the word "session" suggests something already present in their account.

**Wizard fix:** add an "email-style" login step to the wizard itself
(`openseek setup --telegram-login`): ask for the phone number, send the code,
ask for the code and 2FA, store `OPENSEEK_TELEGRAM_SESSION` directly. Never
mention Telethon in the prompt. If a session already exists, offer to reuse it.

**Status:** open. Worked around with `tools/telegram-session.py`.

## 2. 2026-11-07 - Running a helper inside a virtualenv trips users

**What I tried:** `python ~/.config/openseek/venv/bin/python tools/telegram-session.py`.

**What happened:** `SyntaxError: source code cannot contain null bytes` - the
interpreter read the ELF binary as a script.

**Why it hurts:** the documented command requires the reader to understand that
the venv path *is* the interpreter. Typing the familiar `python` prefix is the
natural mistake.

**Wizard fix:** never ask the user to run a Python file by path. Ship a
subcommand (`openseek telegram-login`) or a one-word wrapper on PATH. In docs,
show the exact line and no alternatives.

**Status:** open. Worked around with `~/.local/bin/openseek-session`.

## 3. 2026-11-07 - Supabase "client id and secret" is not a management token

**What I tried:** the provided OAuth client id and `sba_...` client secret
against the Management API.

**What happened:** HTTP 401. Those credentials belong to a Supabase OAuth app
("Sign in with Supabase"), not to project management. The Management API needs
a Personal Access Token that starts with `sbp_`.

**Why it hurts:** both look like "API credentials", and the OAuth app screen is
easy to confuse with the access-token screen. The user loses an hour and still
has nothing that works.

**Wizard fix (done):** detect the `sba_` prefix and print "this is an OAuth app
secret, not a personal access token" plus the exact dashboard URL. Say
"starts with sbp_" in the README, the wizard prompt, and the Vercel guide.

**Status:** open.

## 4. 2026-11-07 - Organizations are invisible to a token, and that looks like "no org"

**What I tried:** `GET /v1/organizations` to pick the organization for the new
project.

**What happened:** `[]` with HTTP 200, while `GET /v1/projects` returned a real
project and `GET /v1/projects/{ref}` exposed `organization_id`.
`GET /v1/organizations/{id}` and `.../members` returned 403.

**Why it hurts:** an empty list reads as "your account has no organization",
which sends the user to create one that they do not need. The truth is that the
token cannot see it.

**Wizard fix:** treat an empty list as ambiguous. Fall back to reading
`organization_id` from an existing project. When every organization endpoint is
403, say "this token cannot read organizations; create a token as the account
owner" instead of "no organizations found".

**Status:** open.

## 5. 2026-11-07 - Creating a project returns a bare 403

**What I tried:** `POST /v1/projects` with a valid organization, name, region,
and database password, three times: existing organization, newly created
organization, and with an explicit plan field.

**What happened:** `{"message":"Forbidden"}` every time. Creating an
organization with the same token succeeded (201), so the token is not simply
read-only. `GET /v1/profile` explains more: "This endpoint requires a
user-scoped access token".

**Why it hurts:** the wizard's whole participant flow starts at project
creation. A generic 403 with no next step is a dead end, and the message does
not name the account or the missing scope.

**Wizard fix:** preflight the token before the wizard starts: call
`/v1/profile`, then list projects, then stop with a named cause. Keep a manual
fallback: "create the project in the dashboard, paste the project ref here" and
verify it with one read. Never let the wizard end on a bare 403.

**Follow-up (same day):** the official CLI fails the same way. Installing
Supabase CLI 3.0.0 and running `supabase projects create openseek-qa-node
--org-id ... --region ap-northeast-1 --db-password ... --yes` ends in
`HTTP POST https://api.supabase.com/v1/projects` then `{"message":"Forbidden"}`.
`supabase orgs list` returns an empty table. The CLI's automatic login refuses
to start without a TTY ("Cannot use automatic login flow inside non-TTY
environments"), so the login must happen in the user's own terminal. The token,
not the client, is the blocker.

**Resolution (same day):** a "supabase login" in a real terminal produced a
user-scoped token. "supabase orgs list" then showed both organizations and
"supabase projects create openseek-qa-node --region ap-northeast-1 --yes"
succeeded (project qilkfmndsuwmopfoihzu). The original token had been created
from an organization-scoped page, not Account -> Access Tokens.

**Status:** fixed.

## 6. 2026-11-07 - A pool channel was created as a broadcast channel

**What I tried:** created a Telegram channel, added the bot as administrator,
generated an invite link.

**What happened:** `GET /api.telegram.org/bot.../getChat` reports
`type=channel`, and Telethon reports `broadcast=True, megagroup=False`. The
README asks for a **supergroup**: "Create a private supergroup (not a broadcast
channel)". Contributions and history scanning do not work the same way.

**Why it hurts:** the Telegram "New Channel" button is the obvious choice, and
nothing in the UI explains the difference. The user only learns it when
contributions silently do nothing.

**Wizard fix:** a preflight check on the channel id. If it is a broadcast
channel, stop and print the difference in one sentence, plus the exact steps to
convert or create a supergroup. Also make `doctor` report the channel kind.

**Status:** open.

## 7. 2026-11-07 - Free plan slot count is invisible until creation fails

**What I tried:** nothing yet; the account already had one project.

**What happened:** the free plan allows two projects. Nothing in the wizard or
the README mentions the limit, so the second participant on one account hits a
wall with no explanation.

**Why it hurts:** the failure arrives at the slowest step, after the user has
already pasted schema and keys.

**Follow-up:** this account now has 2 of 2 free projects
(gamingchannelay@gmail.com's Project and openseek-qa-node). The Deploy Button
path creates a Supabase project through the Vercel integration, so it will fail
on this account unless it reuses the existing project.

**Wizard fix:** count projects before creating one and say "this account has N
of 2 free projects in use". Offer to reuse an existing project instead.

**Status:** open.

## 8. 2026-11-07 - Vercel has two different sign-in paths

**What I tried:** `vercel whoami`, which answered `yatdoescode-8909` with no
token.

**What happened:** the CLI was already authenticated, so no token was needed.
A different user will be asked to log in through a browser, or to create a
token. The Deploy Button path needs a browser click that no CLI can make.

**Why it hurts:** the docs describe the token path and the button path without
saying which one a given user is already in.

**Wizard fix:** detect `vercel whoami` first. If authenticated, skip the token
prompt and say so. If not, offer both paths and mark the button path as
"one click in the browser". Never ask for a token when a session exists.

**Status:** open.

## 9. 2026-11-07 - The Tizen emulator cannot run on this machine as-is (QA only)

**What I tried:** checked KVM, disk, display server, and network to
download.tizen.org.

**What happened:** KVM and network are fine, but only 6.9 GB of disk is free
(Tizen Studio plus a TV image needs roughly 5-6 GB), and `DISPLAY=:0` has no X
server behind it. Java 25 is installed; Tizen Studio expects 17.

**Why it hurts:** the client half of the campaign cannot be verified on this
host, so client tickets wait for a TV or a remote emulator.

**Wizard fix:** not a wizard issue. Track it as QA infrastructure: run the
emulator elsewhere, or connect a TV with developer mode and `sdb connect`.

**Status:** open.

## 10. 2026-11-07 - The CLI login cannot run without a terminal

**What I tried:** "supabase login --no-browser" from a non-interactive shell,
including under a detached process.

**What happened:** "Cannot use automatic login flow inside non-TTY
environments. Please provide --token flag or set the SUPABASE_ACCESS_TOKEN
environment variable." With a real terminal it worked, but the token was stored
in the OS keyring, not in a dotfile, so no file could be reused by another
process.

**Why it hurts:** a wizard that shells out to the CLI cannot log the user in.
It can only reuse a login that already exists, or accept a token explicitly.

**Wizard fix:** detect the CLI session first ("supabase projects list"). If it
works, use it. If not, ask for a token or print the exact two commands to run
in a terminal, and never attempt an automatic browser login from a script.

**Status:** open.

## 11. 2026-11-07 - The REST root answers 401 with a valid key

**What I tried:** smoke-tested the new project with GET /rest/v1/ and the anon
key. Got 401: "Invalid API key ... Only the service_role API key can be used
for this endpoint."

**What happened:** the key was valid. The REST root only accepts service_role,
and auth/v1/health answered 200 with the same anon key.

**Why it hurts:** a maintainer (or a doctor command) that probes the REST root
with the anon key concludes the project is broken and starts rotating keys that
were never wrong.

**Wizard fix:** never health-check /rest/v1/. Use /auth/v1/health, or query a
table the schema created. If a 401 names service_role, say "expected for this
endpoint" in the doctor output.

**Status:** open.

## 12. 2026-11-07 - The documentation promised a bot could read history

**What I tried:** configured a channel node with a bot token, as INSTALL.md and
README.md describe.

**What happened:** the node refused to start. Telegram answers `getHistory` with
`BotMethodInvalidError` for bot clients; history cannot be granted to a bot.
The docs said "make sure it can read channel history" and "grants history +
posting".

**Why it hurts:** an operator follows the docs, hits a refusal, and has no way
to grant the permission the docs asked for.

**Wizard fix:** a bot identity is publishing-only. The node now starts with
`history_readable = false`, the dashboard says "unavailable (bot identity:
publishing only)", and both documents describe the split between a bot
(write) and a user session (read).

**Status:** fixed.

## 13. 2026-11-07 - Channel tile upload used an input shape Telethon rejects

**What I tried:** published a package with the publisher session through the
product's own channel store.

**What happened:** `send_file(entity, (io.BytesIO(data), filename))` raised
"Failed to convert openseek-tile-...jpg to media": Telethon does not accept a
tuple, it read the filename as the file. Every real channel upload would fail.
The unit tests used a fake client that accepted the tuple.

**Why it hurts:** the first self-hoster's first upload fails with a message
that names a JPEG as if it were the problem.

**Wizard fix:** the store now passes `io.BytesIO(data)` plus
`DocumentAttributeFilename`, and the fake mirrors the real signature.

**Status:** fixed.

---

## 14. 2026-11-07 - A numeric channel id stored as text does not resolve

**What I tried:** started the store with `OPENSEEK_TELEGRAM_CHANNEL_ID=-100...`.

**What happened:** `get_entity("-1004391668814")` raises `ValueError` while
`get_entity(-1004391668814)` works. The settings field is a string, so every
numeric channel id failed at startup.

**Why it hurts:** the wizard writes the id as text, so the most natural
configuration could never start.

**Wizard fix:** a `_peer()` helper converts a numeric string to int before
every entity lookup.

**Status:** fixed.
