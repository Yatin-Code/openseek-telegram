# Zero-spend limits for participant-hosted OpenSeek nodes

**Research date:** 2026-11-05

**Context:** [Map #24](https://github.com/Yatin-Code/openseek-telegram/issues/24) · [Research ticket #25](https://github.com/Yatin-Code/openseek-telegram/issues/25)
**Scope:** One Vercel Hobby deployment and one Supabase Free project per participant; each node joins the same Telegram supergroup directly; no shared OpenSeek API and no bot per contributor. Nuvio creates packages locally. The participant accepts throttling, backlog, and downtime to keep spend at zero.

## Resolution

The providers can keep an individual low-traffic node at $0 while it remains inside the free quotas, but the current Vercel profile is not compatible with Hobby as configured: its every-minute Cron is rejected on Hobby. A once-daily Cron is allowed, but its timing can slip by almost an hour and it is too slow to publish contributions promptly. The publication queue needs a request-driven path or users must accept a long pending state.

Two additional constraints need implementation work before this topology is reliable: Vercel Functions cap request and response bodies at 4.5 MB while OpenSeek allows NVMT packages up to 16 MiB; and a horizontally scaled Vercel deployment can open parallel MTProto connections with one Telegram StringSession, which Telegram documents can invalidate that account session. Supabase Free is usable for a rebuildable index and temporary staging at small scale, with owner-operated recovery when the project pauses or quotas trigger restrictions. The intended Telegram read/write scale has no published numeric MTProto user-account throughput limit, so it needs a staged live test with backoff.

This is therefore a best-effort zero-spend design, not an always-on service guarantee. That fits the accepted pause/throttle requirement if each node reports pending/paused state, preserves local Nuvio generation, and retries later.

## Current repository flow

The Vercel guide configures Supabase PostgreSQL as a rebuildable channel index and Supabase Storage as temporary upload staging; Telegram remains the durable store. Nuvio uploads a package to a signed Supabase URL, finalizes it through OpenSeek, and polls until Telegram accepts it. The scheduled route drains the publication queue; its default batch is one item. The repo currently configures that route every minute with a 60-second function duration in [backend/vercel.json](../../backend/vercel.json), and documents the flow in [docs/VERCEL.md](../VERCEL.md). The Vercel profile requires Supabase credentials plus either a Telegram bot token or MTProto StringSession; it rejects a session file because Vercel storage is ephemeral ([backend/openseek/config.py](../../backend/openseek/config.py), [backend/openseek/telegram_mt.py](../../backend/openseek/telegram_mt.py)).

| Function payload size | A Function request body or response body is limited to 4.5 MB; excess payloads return 413. | Signed Supabase staging avoids sending a 16 MiB upload through Vercel, but does not raise the response cap. **Required Vercel change:** remove the one-minute Cron requirement from the Hobby profile. A small bounded drain can run from the upload-finalize/request path, with idempotency and backoff; a daily Cron can remain for housekeeping, not timely publication. Avoid exposing the service-level Cron secret to Nuvio. If publication remains Cron-only, represent accepted contributions as pending until the next run and drain a deliberate bounded batch. The current one-item default will not clear a backlog at useful speed.

## Telegram direct-group constraints

### One-time participant setup

Each contributing node needs a Telegram identity that can read the group and send documents. The repo’s channel setup supports a user login, invite-link join, and a StringSession; the group must allow history reads and Send Messages/Send Media for contributors ([docs/TELEGRAM-POOL.md](../TELEGRAM-POOL.md), [docs/VERCEL.md](../VERCEL.md)). Telegram’s MTProto API requires an application api_id/api_hash; its API is free of charge. Telegram says API clients are monitored, flooding/spamming can lead to permanent bans, and the app must obtain user knowledge and consent for actions performed as that user. A user authorization acts with that account’s identity, so the StringSession is a credential and each participant should opt in explicitly and keep their session private. [Telegram API setup](https://core.telegram.org/api/obtaining_api_id), [API Terms](https://core.telegram.org/api/terms), [user authorization](https://core.telegram.org/api/auth)

For fresh nodes to index existing contributions, the supergroup needs persistent history visible to new members. Telegram documents a supergroup maximum of 200,000 members. Group admins can enable slow mode; when set, a user can send only one message each configured number of seconds. OpenSeek publishes a package as multiple Telegram tile documents, so slow mode can stretch one package across many send intervals ([backend/openseek/channel_pool.py](../../backend/openseek/channel_pool.py)). [Telegram group FAQ](https://telegram.org/faq), [supergroup API](https://core.telegram.org/api/channel), [slow-mode field](https://core.telegram.org/constructor/channelFull)

### Rate limits and shared-session risk

Telegram does not publish a universal numeric messages-per-minute ceiling for ordinary MTProto user sessions in this case. Its error guidance uses dynamic FLOOD_WAIT_X responses and requires the client to wait the returned duration. Slow mode is an additional group-level bound. OpenSeek should honor those waits, pause a participant’s outbox, and retry with backoff rather than treating a flood response as a permanent failure. The aggregate send/read capacity of many independent user sessions in one group is not specified by these sources and remains a scale question. [Telegram API errors](https://core.telegram.org/api/errors)

Telegram’s 20-messages-per-minute-in-a-group guidance is specifically in the Bot FAQ and applies to bots; it is not a published limit for ordinary user-session MTProto. The requested no-bot design should not use that bot number as a user-session promise. If any node is configured with a bot token, apply Telegram’s documented bot-specific limits and visibility rules. [Bots FAQ](https://core.telegram.org/bots/faq)

**Serverless session warning (inference to test):** Telegram documents that parallel main-DC connections using the same authorization key can trigger AUTH_KEY_DUPLICATED and invalidate the authorization key; normally only one main MTProto session is permitted unless Telegram advertises a higher tmp_sessions value. Vercel can scale Functions across concurrent instances, and the current code creates a Telethon client from the configured StringSession in each function runtime. If two runtimes use the same participant session at the same time, the login may be invalidated. Before using StringSession on Vercel, serialize primary Telegram access to one active connection for that account (or prove the chosen client/session strategy follows Telegram’s tmp_sessions allowance) and test overlapping cold starts. Never reuse one participant’s session across participants. [Telegram API errors](https://core.telegram.org/api/errors), [Vercel Function limits](https://vercel.com/docs/functions/limitations), [OpenSeek Telegram client](../../backend/openseek/telegram_mt.py)

### Setup-wizard feasibility

The repository has a local channel-pool setup wizard that can log in, join an invite, check access, and write a protected local environment file. The Vercel guide still requires a participant to create a Supabase project, apply the schema, create the staging bucket, configure Vercel environment variables, and deploy; that is not currently an end-to-end Vercel/Supabase provisioning wizard ([docs/TELEGRAM-POOL.md](../TELEGRAM-POOL.md), [docs/VERCEL.md](../VERCEL.md)).

A future one-time wizard can automate or guide the user session and group-permission steps, but a successful login alone is not a Vercel readiness check. The wizard should validate that Nuvio reads fit the 4.5 MB Function response limit or use a bounded chunk path, and flag the StringSession concurrency risk until one-account/one-primary-connection behavior is enforced and tested under multiple function instances. The 4.5 MB cap is an OpenSeek read-path limit, not a reason the participant cannot create a Telegram session; the parallel-session risk can invalidate the participant’s Telegram authorization and therefore blocks a smooth “setup once and forget it” promise until resolved. [Vercel Function limitations](https://vercel.com/docs/functions/limitations), [Telegram API errors](https://core.telegram.org/api/errors)

## Design changes and open scale check

1. **Make publication event-driven on each node.** Trigger bounded queue draining from the authenticated finalize path or another request already made to that participant’s own deployment; keep Cron only for cleanup at a Hobby-compatible daily cadence. Use durable queue state, idempotent Telegram writes, Retry-After/backoff for FloodWait and provider outages, and slow client polling. Playback should remain local if the node or shared group is paused.
2. **Keep every package response within Vercel limits.** Either return validated tile/slot chunks small enough to stay below 4.5 MB, or reduce the maximum returned package size and make Nuvio fall back to local generation on an oversized/missing result. The signed Supabase upload path solves only the Function request-size side.
3. **Control Telegram connections per participant.** Establish the user session once during setup, store only that participant’s StringSession in their own Vercel secret environment, and serialize primary MTProto connections across function instances. Handle Telegram slow mode and FLOOD_WAIT as deferred work.
4. **Make pauses visible and recoverable.** Show Supabase paused/quota-restricted and Telegram-backoff states; allow the node owner to resume Supabase; retain local Nuvio generation and retry pending contributions when service returns. Never silently upgrade to a paid plan.
5. **Validate scale with real accounts before calling it supported.** Test a few participant deployments with distinct user sessions in one persistent-history supergroup, concurrent Vercel cold starts, duplicate/retried uploads, and a backlog. Measure Vercel invocation/origin-transfer usage, Supabase database/storage/egress, Telegram FLOOD_WAIT and AUTH_KEY_DUPLICATED, and actual time to index new posts. No official source gives a safe user-session rate for the target scale.
